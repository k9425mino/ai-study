# CodeRabbit 운영 모범 사례

## 1. 단계적으로 도입하기

처음부터 설정을 가득 채우지 않습니다.

1. 기본 설정으로 1~2주간 실제 PR을 리뷰합니다.
2. 반복되는 오탐과 누락을 기록합니다.
3. `profile`, `path_filters`, `path_instructions` 순서로 최소한만 조정합니다.
4. 설정 변경 전후의 리뷰 품질을 비교합니다.

## 2. 작은 PR을 유지하기

AI 리뷰도 변경이 작고 목적이 하나일 때 더 정확합니다.

- 기능, 리팩터링, 포맷 변경을 가능하면 분리합니다.
- PR 설명에 목적, 비목표, 위험 영역, 검증 방법을 적습니다.
- 자동 생성 파일은 별도 커밋으로 분리하거나 리뷰 대상에서 제외합니다.
- 큰 PR에서는 Change Stack의 Cohort가 자연스럽게 분리되는지 확인합니다.

## 3. 프로젝트 규칙을 한곳에서 관리하기

- 여러 AI 도구가 함께 읽어야 하는 공통 규칙은 `AGENTS.md`에 둡니다.
- 특정 경로에서만 필요한 리뷰 기준은 `path_instructions`에 둡니다.
- 이미 문서화된 규칙을 여러 설정 파일에 중복 복사하지 않습니다.
- “좋은 코드를 작성한다”보다 “외부 입력은 스키마로 검증한다”처럼 확인 가능한 문장으로 씁니다.

## 4. 노이즈를 관리하기

- 코멘트가 너무 많으면 `profile: chill`부터 적용합니다.
- 생성물, 의존성, lock 파일을 `path_filters`로 제외합니다.
- 스타일은 기존 린터와 포매터에 맡기고 CodeRabbit에는 로직, 보안, 오류 처리에 집중하도록 지시합니다.
- 반복적으로 가치가 낮은 제안은 무시만 하지 말고 설정이나 학습 피드백으로 반영합니다.

## 5. 심각한 문제부터 처리하기

1. 재현 가능한 Critical과 Major 문제
2. 보안, 데이터 무결성, 하위 호환성 문제
3. 누락된 오류와 경계 조건
4. 유지보수성 개선
5. 스타일과 사소한 제안

모든 코멘트를 해결해야 머지할 수 있다는 규칙은 오히려 중요한 문제를 흐릴 수 있습니다.

## 6. 사람의 책임을 유지하기

CodeRabbit의 제안을 반영하기 전에 다음을 확인합니다.

- 실제 요구사항과 일치하는가?
- 테스트나 코드로 문제를 재현할 수 있는가?
- 수정으로 새로운 복잡성이나 회귀가 생기지 않는가?
- 현재 PR 범위에서 해결해야 하는가?
- 보안이나 도메인 판단이 필요한 경우 담당자가 검토했는가?

AI 리뷰는 사람 리뷰를 줄이는 도구가 아니라, 사람이 더 중요한 판단에 시간을 쓰게 하는 보조 수단입니다.

## 7. 로컬과 PR 리뷰의 역할을 나누기

- 로컬 CLI: 구현 직후의 빠른 피드백과 커밋 전 점검
- PR 리뷰: 팀 협업, 전체 변경 맥락, 토론과 승인 기록
- 기존 CI: 결정적인 테스트, 타입 검사, 린트, 보안 스캔

세 계층을 함께 사용하되 같은 역할을 중복시키지 않습니다.

## 도입 체크리스트

- [ ] GitHub App의 저장소 접근 범위를 최소화했는가?
- [ ] 기본 설정으로 실제 PR을 충분히 관찰했는가?
- [ ] `.coderabbit.yaml`이 루트에 있고 스키마 검증을 통과하는가?
- [ ] 기본 브랜치와 추가 대상 브랜치 정책이 맞는가?
- [ ] 생성물과 불필요한 파일이 리뷰에서 제외되는가?
- [ ] 경로별 지침이 짧고 검증 가능한가?
- [ ] Critical과 Major 문제의 처리 기준이 합의되어 있는가?
- [ ] 오탐을 반박하고 사람 판단을 남길 리뷰 문화가 있는가?
- [ ] 로컬 리뷰 반복 횟수와 종료 조건이 정해져 있는가?
- [ ] 가격, 데이터 처리, 보존 정책을 공식 문서에서 확인했는가?
