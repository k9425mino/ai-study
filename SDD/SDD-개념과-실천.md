# SDD(Spec-Driven Development) 개념과 실천

> 정리 기준일: 2026-07-26

## 한 줄 정의

SDD는 코드를 작성하기 전에 **무엇을 왜 만들고, 어떤 조건을 만족해야 완료되는지** 명세하고, 그 스펙을 개발과 검증의 공통 기준으로 사용하는 개발 방법론입니다.

AI 코딩에서는 프롬프트 대화가 사라져도 스펙은 저장소에 남습니다. 개발자와 AI 에이전트는 같은 스펙을 읽고 구현·리뷰·테스트를 수행하므로, 스펙이 작업의 단일 기준점 역할을 합니다.

## 왜 필요한가?

AI는 코드를 빠르게 만들지만, 부족한 맥락은 그럴듯한 추측으로 채우는 경향이 있습니다. 요구사항과 제약이 불명확하면 다음 문제가 발생하기 쉽습니다.

- 기존 아키텍처와 다른 패턴으로 구현합니다.
- 이전에 내린 기술 결정과 모순되는 코드를 만듭니다.
- 예외 상황, 보안, 하위 호환성, 테스트를 놓칩니다.
- 세션이나 작업이 바뀔 때 같은 맥락을 반복해서 설명해야 합니다.
- 구현량은 늘지만 수정과 재작업 비용도 함께 증가합니다.

SDD는 좋은 코드를 직접 보장하는 마법이 아닙니다. 대신 AI와 사람이 잘못된 문제를 빠르게 구현하지 않도록, 구현 전에 의도와 성공 조건을 고정하는 장치입니다.

## 스펙 권한의 세 단계

SDD는 프로젝트 상황에 따라 스펙을 어느 정도까지 유지하고 강제할지 선택합니다.

| 접근 | 스펙의 역할 | 적합한 상황 | 주의점 |
| --- | --- | --- | --- |
| Spec-first | 구현 전에 방향을 명확히 하는 출발점 | SDD를 처음 적용하는 팀, 단기 기능 | 구현 후 스펙이 낡을 수 있음 |
| Spec-anchored | 코드와 함께 갱신되는 지속적인 기준 | 장기 운영, 여러 팀, 감사 추적 | 스펙 유지 비용이 발생 |
| Spec-as-source | 스펙 변경이 코드 생성을 직접 이끔 | 성숙한 코드 생성·검증 파이프라인 | 비결정적 생성 결과에 대한 강한 검증 필요 |

대부분의 팀은 Spec-first로 시작해, 오래 유지할 핵심 기능만 Spec-anchored로 관리하는 혼합 방식이 현실적입니다.

## 다른 개발 방식과의 관계

### 바이브 코딩과의 차이

바이브 코딩은 짧은 지시로 즉시 결과를 만드는 데 강합니다. 버릴 프로토타입이나 작은 독립 작업에는 효율적이지만, 범위가 커지면 맥락 소실과 구조적 일관성 문제가 커질 수 있습니다.

SDD는 구현 전에 스펙을 만들고 검토해 AI가 임의로 채울 영역을 줄입니다. 탐색 단계에서는 바이브 코딩으로 빠르게 실험하고, 유지할 방향이 정해지면 SDD로 전환할 수 있습니다.

### TDD·BDD와의 관계

- TDD는 테스트를 먼저 작성해 코드 단위의 정확성과 설계를 이끕니다.
- BDD는 사용자 행동과 기대 결과를 시나리오로 합의합니다.
- SDD는 기능 범위, 시스템 제약, 기존 결정, 검증 기준까지 포함한 상위 계약을 제공합니다.

서로 대체 관계가 아닙니다. 스펙의 인수 조건을 BDD 시나리오로 구체화하고, 구현 과정에서 TDD를 사용하는 조합이 가능합니다.

## 좋은 스펙의 핵심 요소

### 1. 목표와 사용자 결과

기능 이름이 아니라 완료 후 사용자가 할 수 있는 일을 적습니다.

```text
나쁜 예: 로그인 기능을 만든다.
좋은 예: 등록 사용자가 이메일과 비밀번호로 로그인하고,
         새로고침 후에도 인증 세션을 유지할 수 있다.
```

### 2. 범위와 비범위

포함할 기능뿐 아니라 이번 작업에서 하지 않을 일도 명시합니다. 비범위가 없으면 AI가 흔한 부가 기능까지 임의로 추가할 수 있습니다.

### 3. 제약과 가정

기존 기술 스택, 성능 목표, 보안 규칙, 외부 API 제한, 호환성 요구사항처럼 구현 선택에 영향을 주는 조건을 적습니다.

### 4. 이미 결정된 사항

데이터 저장 방식, 인증 라이브러리, 공개 API 계약처럼 다시 논의하지 않을 결정을 기록합니다. 결정 이유가 중요하면 ADR로 분리해 연결합니다.

### 5. 인수 조건과 예외 상황

정상 경로뿐 아니라 실패, 경계값, 권한 부족, 중복 요청, 네트워크 오류 같은 상황에서 기대하는 동작을 검증 가능한 문장으로 적습니다.

### 6. 작업 분해

한 번에 전체 기능을 생성하지 않고 독립적으로 구현하고 검증할 수 있는 작업으로 나눕니다. 병렬 작업은 같은 파일이나 계약을 동시에 바꾸지 않는 경우에만 수행합니다.

### 7. 검증 기준

“잘 동작한다”가 아니라 실행할 테스트와 관찰할 결과를 적습니다.

```text
- 잘못된 자격 증명에는 어느 필드가 틀렸는지 노출하지 않는다.
- 5회 연속 로그인 실패 후 15분간 계정을 잠근다.
- 비밀번호 평문이 저장소, 데이터베이스, 로그에 남지 않는다.
- 단위 테스트와 인증 통합 테스트가 통과한다.
```

## SDD 실행 방법

### 1단계: 스펙이 필요한 작업인지 판단

다음 중 하나라도 해당하면 스펙 작성 비용을 들일 가치가 큽니다.

- 여러 세션, 담당자, 서비스에 걸친 작업
- 잘못 이해했을 때 되돌리는 비용이 큰 기능
- 공개 API, 데이터 모델, 보안 경계를 변경하는 작업
- 규정 준수나 의사결정 기록이 필요한 작업
- 코드만 보고는 제품 의도를 알기 어려운 작업

몇 분 안에 결과를 검토할 수 있는 기계적 수정, 폐기할 실험, 작은 오타 수정에는 상세 스펙이 오히려 낭비일 수 있습니다.

### 2단계: 프로젝트 공통 맥락 정리

`AGENTS.md`, 아키텍처 문서, 코딩 규칙, 기존 ADR처럼 모든 기능에 적용되는 정보를 먼저 정리합니다. 기능 스펙에는 공통 규칙을 복사하지 말고 필요한 문서를 연결합니다.

### 3단계: 기능 스펙 작성

기술 구현보다 사용자 문제와 기대 행동을 먼저 적습니다. 모르는 내용을 추측하지 말고 질문이나 `미정` 항목으로 남깁니다.

### 4단계: 사람과 AI가 함께 명확화

각 요구사항에 대해 다음을 질문합니다.

- 주체와 권한은 누구에게 있는가?
- 입력과 출력은 무엇인가?
- 실패하면 어떤 상태와 메시지를 남기는가?
- 중복, 순서 변경, 동시 실행에서는 어떻게 동작하는가?
- 기존 데이터와 API의 호환성을 유지해야 하는가?

답은 대화에만 남기지 말고 스펙에 반영합니다.

### 5단계: 기술 계획 작성

스펙이 합의된 뒤 구현 방법을 정합니다. 변경 경로, 데이터 모델, API 계약, 의존성, 마이그레이션, 테스트 전략, 배포와 롤백 계획을 포함합니다.

### 6단계: 검증 가능한 작업으로 분해

각 작업에 입력, 결과물, 선행 작업, 검증 방법을 붙입니다. 기반 작업을 먼저 배치하고 사용자 스토리별로 수직 분할합니다.

### 7단계: 작은 단위로 구현하고 검증

한 작업을 구현한 뒤 테스트와 스펙을 대조합니다. 구현 에이전트와 별도의 검증자에게 스펙 위반과 누락을 찾게 하면 자기 검증의 낙관 편향을 줄일 수 있습니다.

### 8단계: 변경된 진실을 스펙에 반영

구현 중 요구사항이나 결정이 바뀌면 코드만 수정하지 않습니다. 스펙과 계획을 먼저 갱신하고, 영향받는 작업과 테스트를 다시 생성합니다.

## 간단한 스펙 템플릿

```markdown
# 기능명

## 배경과 목표
- 해결할 사용자 문제:
- 완료 후 기대 결과:

## 범위
### 포함
- ...

### 제외
- ...

## 사용자 시나리오
1. Given ...
2. When ...
3. Then ...

## 기능 요구사항
- FR-001: 시스템은 ...해야 한다.

## 제약과 기존 결정
- 기술·보안·성능·호환성 제약:
- 연결할 AGENTS.md 또는 ADR:

## 예외와 경계 조건
- 입력이 비어 있으면 ...
- 요청이 중복되면 ...

## 인수 조건
- [ ] ...

## 검증 방법
- 자동 테스트:
- 수동 확인:
- 관찰 지표:

## 미정 사항
- [ ] 결정이 필요한 질문
```

## 흔한 실패와 대응

| 실패 | 대응 |
| --- | --- |
| 구현 방법을 요구사항 단계에서 고정 | 무엇과 왜는 스펙, 어떻게는 계획으로 분리 |
| 비범위가 없어 기능이 계속 늘어남 | 명시적인 제외 목록과 변경 절차 추가 |
| 첫 스펙을 완성본으로 취급 | 명확화와 구현 피드백을 반영해 갱신 |
| 스펙과 코드가 서로 다름 | 테스트·CI·리뷰에서 스펙 기준 검증 |
| 문서 작성에만 과도한 시간 사용 | 오해 수정 비용보다 스펙 비용이 커지면 구현 시작 |
| AI가 생성한 작업을 한 번에 실행 | 의존성 순서대로 나누고 단계별 사람 검토 |

## 완료 체크리스트

- [ ] 사용자의 기대 결과가 기능 이름보다 구체적인가?
- [ ] 포함 범위와 제외 범위가 모두 있는가?
- [ ] 중요한 가정과 기존 결정이 기록되었는가?
- [ ] 정상·실패·경계 조건이 검증 가능한가?
- [ ] 구현 세부사항이 요구사항과 분리되어 있는가?
- [ ] 작업별 완료 기준과 검증 명령이 있는가?
- [ ] 코드 변경으로 달라진 사실이 스펙에도 반영되었는가?
- [ ] 현재 작업 규모에 비해 스펙이 과도하지 않은가?
